# Router dell'ambito — piano di implementazione

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (esecuzione nativa, scelta dell'utente). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** un nodo LLM `nodo_router` prima dell'agente che manda le domande fuori ambito a `nodo_rifiuto`, con l'ambito letto da `ambito.txt`.

**Architecture:** `assistente/router.py` contiene schema JSON, prompt, scelta dei messaggi e lettura della decisione; `costruisci_grafo(modello, strumenti, ambito=None, modello_router=None)` aggiunge router e rifiuto solo se riceve l'ambito. La decisione passa all'arco condizionale tramite un campo `categoria` dello stato, non nella cronologia. Output strutturato con `with_structured_output(SCHEMA_ROUTER, method="json_schema", include_raw=True)`: gli errori di lettura tornano come `parsing_error` (→ si procede come conversazione), quelli di connessione risalgono come oggi.

**Tech Stack:** Python 3.14.7, LangGraph, `langchain_core`, `langchain-openai` (già presenti). Nessuna dipendenza nuova.

**Spec:** `docs/superpowers/specs/2026-11-09-router-design.md`

## Verifica tecnica già fatta (09/11/2026, prove usa e getta con gemma-4-e4b)
- `method="json_schema"` funziona; `method="function_calling"` → errore 400 da LM Studio.
- Con il ragionamento attivo una decisione richiede ~50 s (~240 token di ragionamento a ~6 token/s); con
  `reasoning_effort="none"` ~9 s e 0 token di ragionamento, con decisioni corrette.
- Con un prompt generico «Quanti giorni mancano a Natale?» finiva fuori ambito; con il prompt che elenca ciò che
  gli strumenti coprono e «in caso di dubbio conversazione» le 8 domande di prova sono classificate bene.
- Una volta, anche con `reasoning_effort="none"`, il modello ha ragionato fino a 8192 token e la libreria ha
  sollevato `LengthFinishReasonError` (un'eccezione, non un `parsing_error`).
- Quindi: il router usa un **suo client del modello** con `reasoning_effort="none"` e `max_tokens=80`; **qualsiasi**
  eccezione del router (o decisione illeggibile) fa passare la domanda all'agente con un WARNING: se il modello è
  davvero irraggiungibile, l'errore arriva comunque dalla chiamata dell'agente, come oggi. L'agente resta com'è.

## Global Constraints
- Categorie: `"conversazione"`, `"fuori_ambito"`. Log: `router: conversazione (<motivo>)`, `router: fuori ambito (<motivo>)`, `nodo_rifiuto: domanda fuori ambito`.
- Rifiuto: `"Posso aiutarti solo con domande scientifiche o sul laboratorio: <motivo>"` seguito da un punto, senza doppio punto se il motivo finisce già con `.`.
- Nessun import di `pydantic`, `openai`, `httpx` in `assistente/`; lo schema è un dizionario.
- Variabile facoltativa `AMBITO_FILE` (default `ambito.txt`, relativo alla cartella di lavoro come `.env`).
- Branch `feature/router`; Conventional Commits in italiano con `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`; staging selettivo; niente merge né push.

## Review Focus
1. Domanda di seguito («e domani?» dopo una domanda sulle date): il router vede la domanda precedente. Test in Task 2.
2. Cronologia con richieste di strumenti e `ToolMessage`: al router arrivano solo domande e risposte testuali. Test in Task 2.
3. Output del router con categoria sconosciuta, `parsed` nullo o `parsing_error`: WARNING e agente chiamato. Test in Task 2.
4. Turno dopo un rifiuto: la cronologia contiene domanda e rifiuto, il turno successivo in ambito funziona. Test in Task 2.
5. Il limite dei passaggi non si riduce per l'agente: con il router un turno con 4 giri di strumenti passa ancora. Test in Task 2.
